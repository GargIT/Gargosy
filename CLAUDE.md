# Gargosy — Agent Map
> Source of truth for LLM agents working on this codebase. Read it before touching any file, and update it when you create, split or move a file.

## Project Overview
Gargosy is a Flutter app for Windows that browses a RomM library, downloads ROMs, launches emulators that Gargosy installs itself, and syncs saves and states with RomM. It looks and feels like RomM's v2 web UI, is controller-first, is always portable, and supports several profiles (one RomM user each) on one PC. State management is Riverpod.

It is built on code copied from Freegosy (MIT, © 2026 abduznik). There is no shared history; upstream fixes are copied by hand when needed.

## Rules (MANDATORY)
- **Portable only.** Every path comes from the app root (the folder of `Gargosy.exe`): `roms\`, `emulators\`, `bios\`, `userdata\`. Never AppData, never `path_provider` application dirs.
- **ROM folders hold only ROMs.** Never write saves, zips, backups or metadata into `roms\`.
- **Every write goes through `PathGuard`** (`lib/profiles/path_guard.dart`). It allows only the active profile's folder, `userdata\templates\`, `userdata\app\`, `userdata\settings.json`, `roms\`, `emulators\` and `bios\`. Paths from the server (file names, save targets) are checked the same way. **The one exception:** `GargosyUpdate.exe` (`windows/updater/`, native, after Gargosy exits) replaces the app files listed in the release's `app-files.txt` and nothing else; no Dart code writes the app files.
- **The active profile is the only source of paths and of the RomM session.** Services take a `ProfileContext` through Riverpod; no global "current user", no static paths.
- **One emulator process at a time.** Never launch while a game runs, and never switch profiles during a game or an unfinished sync.
- **An emulator is pointed at the profile's data folder** by a command-line argument, by writing its folder settings just before launch, or, for one that only reads a folder next to its exe, by a folder link (a junction) from there to the profile, re-pointed per launch (`ProfileLaunchConfig`, `LinkedFolderConfig`). A link is a pointer, not a swap: nothing is copied. Never swap saves in and out of a shared folder. An emulator that can't be pointed is not supported. `docs/emulator-profiles.md` records how each one is done.
- **Credentials:** RomM tokens are DPAPI-encrypted, one file per PC (`login.<PC>.dpapi`). Never store a password. A PIN is a salted hash, and it's a family lock, not security.
- **Look and feel = RomM v2, dark only.** Theme values live in `lib/ui/theme/tokens.dart`. Copy token *values* only: no RomM code, CSS, icons or logo (RomM is AGPL-3.0).
- **Controller-first.** Every screen must work with a controller alone: spatial focus, B goes back, LB/RB switch tabs, and focus is remembered per screen. Mouse and keyboard must work too.
- **Copied code is marked.** A file copied from Freegosy starts with `// Adapted from Freegosy (MIT, © 2026 abduznik).`, and its tests come along with it.
- Aim for files under 600 lines. When a file is over it, or a change would push it over, move self-contained parts (a class, a parser, a group of pure functions, a dialog or sub-widget) to a helper file when the result is clearer. A cohesive unit (e.g. a data table) may stay whole.
- All RomM API calls go through `romm_service.dart` only. Never call the API from UI or providers.
- All emulator logic goes through the strategy pattern; never hardcode emulator behaviour in the UI.
  - A new emulator is a new file in `core/emulator/strategies/`, registered in `strategy_registry.dart` only.
  - A new save strategy is a new file in `core/save/strategies/`, registered in `save_sync_service.dart` only.
- Providers are thin: they call services and hold no business logic.
- New screen = new file in `ui/screens/`; new reusable widget = new file in `ui/widgets/`.
- Never use `Platform.environment` or `Platform.isWindows` directly. Use `PlatformInfo` (`core/platform/platform_info.dart`) passed in as a constructor parameter.
- ROM name sanitization includes `!` in the regex, the same in every service that builds a ROM folder name.
- Windows games are folder-based: `findMainRomInFolder()` returns the folder for `windows`/`pc`/`win`.
- A save strategy that needs a game id (serial, title id) takes RomM's `Game.titleId`/`saveTarget` through `GameIdResolver` before reading the ROM itself; with RomM's id it never opens the disc.
- RomM calls from UI go through the providers in `lib/providers/` (which use `RommService` / `LibraryApi`).
- Downloads stage in `userdata\app\temp`; `roms\` only ever receives complete ROMs.
- Write files with LF line endings (`.gitattributes` normalizes). From Python, use `open(..., 'w', newline='\n')`.
- Commit messages, PR titles and PR descriptions never contain a link to the session that made them (no `claude.ai/code/session_…` line).

## Layout on disk
```
Gargosy\
  Gargosy.exe, *.dll, data\…     app (data\ is Flutter's); replaced on update
  roms\<platform>\               ROMs only, shared
  emulators\<emu>\               emulator binaries, shared
  bios\                          firmware, shared
  userdata\
    settings.json
    app\logs\                    gargosy-<yyyyMMdd-HHmmss>.log, one per start, newest 10 kept
    templates\<emu>\             starting emulator data for new profiles
    profiles\<id>\               profile.json, login.<PC>.dpapi, emulators\<emu>\, backups\, cache\
```

### Entry points
- `lib/main.dart` — finds the root (`AppRoot.fromArgs`; `--root=<dir>` for `flutter run`), checks it can be written (else `StartupErrorApp`) and that `sigil.dll` loads (else `StartupErrorApp.sigil`, #57: no save code without sigil), points `path_provider`, `shared_preferences` and TMP/TEMP (`profiles/portable_temp.dart`) into `userdata\`, starts the window, runs `GargosyApp`.
- `lib/app.dart` — `GargosyApp`: theme, `InputRouter`, F11; the profile picker when no profile is active, else `AppShell`. A profile switch pops every pushed page.

States the same way: `RommService.getSharedStatesOrNull` (`all_user_states`) → `ResumeService(sharedStates:)` lists them after the player's own as `ResumeEntry.owner` entries (with state sync off too; never preselected, `PlayView.ownStateCount`, `StateList` groups them by player). `PlayController.resume` takes one through `PlayEngine.takeSharedState` (`play/state_copies.dart`: `copySharedState`, with `stateForThisPc` and `resumeTempDir` for Resume's other copies; `ResumeService.downloadShared`): an emulator that loads a state from any path (`EmulatorStrategy.loadsStateFromPath`) starts from a copy in `userdata\app\temp\resume\` (deleted after the session); RetroArch, ares and Flycast load a slot by number, so it goes into the player's first free slot (`ResumeService.freeSlotFor`, `StateSyncCapable.stateFileForSlot`; a slot synced before counts as used) and is theirs from then on. Share (part 3): `RommService.setSaveShared` / `setStateShared` (`PUT /api/saves|states/{id}/visibility`, owner only) through `SaveActions.share` (allowed while a game runs: only RomM changes); Y on the player's own RomM save (`SaveList.onShare`, also in the click menu) or state (`StateList.onShare`) on the Saves tab; `SaveEntry.shared` / `ResumeEntry.shared` (`RommState.isPublic`) give the teal "shared" tag.
- Deleting on the Saves tab (#94): `play/save_deletion.dart` — `deleteSaveEntry` (RomM, backup, or this PC's), `deleteLocalSave` (the plan, `SaveStrategy.saveDeletionFor` → `core/save/local_save_deletion.dart`'s `LocalSaveDeletion`: files, save folders, cards written again; by default the game's save files, all inside `getSaveDir`, refused with why for a shared card (`pullMustFinishBeforeLaunch`). `SigilSaveStrategy` plans from sigil's collect: the files it read (`SigilCollected.reads`) are a Game Boy or N64 save; elsewhere `sigil/sigil_save_deletion.dart`'s `planSigilSaveDeletion`: a file in a save folder (PCSX2 folder card, PSP `SAVEDATA`) takes its folder, a PS1/PS2 card file loses the saves on sigil's unit (`Ps1MemoryCard.withoutSaves`, `Ps2MemoryCard.withSaves([], …)`), anything else refused; GameCube and Dreamcast refused. Then backed up (`PlayPreparer.backUp`), every card and folder copied whole into `backups\deleted\<time>\`, applied through the profile's `PathGuard`, and `SaveStrategy.afterSaveDeleted` drops sigil's last sync (`SigilStateStore.forget`) so RomM's save comes back as new), `deleteOwnState` (the file and `StateSyncCapable.stateSidecars`, the sync record (`ResumeService.forgetState`), RomM's copy via `RommService.deleteStates`; never another player's). `SaveActions.deleteState`; hold A or a click on This PC rows (`SaveList`) and on the player's states (`StateList.onDelete`, the Saves tab's state menu).

### Updates (issue #16)
- `update/update_version.dart` — `UpdateVersion`: the version from `Gargosy-<version>.zip`, semver order (`pub_semver`; `0.2.0-preview.3 < 0.2.0-preview.10 < 0.2.0`), never a downgrade.
- `update/update_checker.dart` — `UpdateChecker`: GitHub Releases without a token (Latest: `releases/latest`; Preview: `releases?per_page=10`, newest of all), one check a start and none within 6 h unless forced, ETag/304, `UpToDate | UpdateAvailable(ReleaseInfo) | CheckFailed`. App-wide prefs `update.channel`, `update.autoCheck`, `update.lastCheck`, `update.etag`, `update.lastResult`.
- `update/update_downloader.dart` — the zip into `userdata\app\update\` (size, SHA-256 `digest`), unpacked to `update\Gargosy\` without the user's folders, layout checked (`unpackUpdate`). `update/app_files.dart` — `AppFiles.parse` (the same rules as the updater's `IsSafeRelative`). `update/update_paths.dart`.
- `update/update_installer.dart` — `UpdateInstaller`: `canInstall` (updater present, not under Program Files), `start` (copies `GargosyUpdate.exe` into `update\`, starts that copy detached with `--pid --root --from --version --old-version -- <args>`), `afterStart` (`--updated-from=` cleans up; `--update-failed` reads `update.log`'s last line).
- `providers/update_providers.dart` — `launchArgsProvider`, `updateOutcomeProvider` (set in `main.dart`), `updateAutoCheckEnabledProvider` (off in `app_harness.dart`), `appQuitProvider`, `updateStateProvider` (check at start from `app.dart`, Check now, channel).

- `windows/updater/` — `GargosyUpdate.exe` (Win32 C++, static CRT, built by `windows/CMakeLists.txt` and on its own): waits for the PID (60 s), moves the old listed files to `update\previous\`, copies the new ones, rolls back on any failure, starts Gargosy with `--updated-from=` / `--update-failed`. ## Testing
- `flutter_test` + `mockito` (`@GenerateMocks` + `build_runner`) + `fake_async`. HTTP is faked with `test/helpers/fake_dio_adapter.dart`.
- `test/helpers/widget_env.dart`: `testApp()` frames a widget (theme, input, covers as boxes, a Gargosy folder that doesn't exist unless `root:` is given) and `press()` sends a controller button (the D-pad moves focus like GamepadService). Fakes: `fake_library_api.dart`, `fake_download_service.dart`, `game_fixtures.dart`.
- `test/helpers/app_harness.dart` builds the whole app with fakes (protector, PC identity, RomM auth); its `settle()` lets file IO and timers finish (one round per sequential async step).
- `test/unit/` holds logic; `test/widgets/` holds widgets, including focus and controller navigation.
- Required tests:
  - profiles never share a path;
  - `PathGuard` rejects anything outside the allowed folders;
  - each emulator's `ProfileLaunchConfig` arguments or written keys;
  - device pairing states;
  - the pre-launch pull (late pull writes nothing, failures don't block).
- Gate: `dart format lib test tool && flutter analyze && flutter test` (CI runs the same on `windows-latest`, with the format step as a check: `--set-exit-if-changed`). The page width is 120 (`analysis_options.yaml`). CI also runs `powershell -File tool/test_updater.ps1` (builds `windows/updater` with CMake and tests `GargosyUpdate.exe`).

## Release
`pwsh tool/make_release.ps1` builds and writes `dist\Gargosy-<version>.zip`: it unpacks to `Gargosy\` with the app, empty `roms\`, `emulators\`, `bios\` and `userdata\`, and the licence files. There is no installer. An update replaces only the app files.
